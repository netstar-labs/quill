# Decisions

Choices made where the design left room. Newest last. **Every row was accepted by the owner on 2026-10-28**; a row that carries its own date records a specific answer or
request given that day, and a rejected row would be
struck through and kept. "The reference" is the existing implementation reviewed in [review.md](review.md).

| # | Decision | Why |
|---|---|---|
| 1 | The project is **quill**: package `quill`, module `github.com/netstar-labs/quill`, CLI `quill`. The library is the root package, with `cmd/`, `internal/`, `examples/` and `docs/` beside it. **Accepted 2026-10-28.** | A short name that is easy to type. |
| 2 | **Build fresh** from this design, porting the reference's behavioural tests that still apply, instead of deleting code from the reference. | The sharding, frontier and read-only logic is woven through the reference's single large core file; deleting it in place risks leaving half of it behind. Tests carry its hard-won recovery behaviour, so they travel; the code is rewritten smaller. |
| 3 | **The frame bytes are the reference's, unchanged**; file names, state files and layout are free to change. **Accepted 2026-10-28**, "unless there is a performance advantage to altering it". | None found: the reference's own profiles (**reported**) show appends bound by memory copying and allocation and reads by syscalls (85% of read CPU), not by decoding, so the frame is not the bottleneck. The golden tests that pin the frame stay valid. |
| 4 | **A log is a directory.** `Open(dir)` returns a `Log` for one topic and takes that directory's lock. Multiple topics are multiple logs, in one process or several. **Accepted 2026-10-28.** | A directory is the unit of ownership, state, retention, backup and deletion. It removes the topic registry, the case-collision check, the 230-byte topic limit, per-topic maps in every state file and the global byte cap, and lets different processes own different topics. Cost: many topics mean many directories, locks and descriptors. |
| 5 | **One lane per log.** Sequence numbers are assigned under the log's mutex; there is no router and no CAS counter. | At one lane file order is sequence order: no merge, no cross-shard frontier, `ScanAll` ordered. Measured on the reference: reads 3–5× faster from the start of a log than at four shards ([review.md](review.md), finding 1). |
| 6 | **A per-log format marker file, `quill.format`**, holds `quill/1` and a random 128-bit **log ID** in hex (`quill/1 3f9a…`); written when a log is created, required on open. A marker newer than quill knows is refused with `ErrFutureVersion`. **Accepted 2026-10-28.** | The reference's frame has no version (a documented limitation), so a format change cannot announce itself. A marker file fixes that without changing the frame; a header in each segment would change the bytes. The log ID ties a consumer's offset file to the log it belongs to, so a log that is recreated or replaced does not silently inherit offsets (decision 36). |
| 7 | **Variable-length frames only.** The fixed-width format and its configuration are cut. | A second recovery path and three of the reference's thirteen documented limitations, for an O(1) cold start that `.idx` sidecars can provide later. |
| 8 | **`quill.tail` is the single durable marker.** One small strict-JSON file `{seq, seg, off, maxseg}`: the last durable sequence, the active segment id and byte offset that are durable, and the highest segment id ever used. The writer rewrites it (temp file, fsync, rename, no directory fsync) after each flush that changed it, and before any segment is deleted. A `Reader` reads up to it and no further, and does **not** probe whether a writer is live. **No feed for a shipper. Accepted 2026-10-28** (a marker for external readers; nothing for a shipper); the choice to trust the marker alone, with no liveness probe, **confirmed 2026-10-28**. | The marker closes the hazard that a reader sees bytes still in the page cache which an OS crash would drop and the writer would later reuse. It also replaces separate head, segment-id and frontier files: the head survives expiry of every segment because the marker keeps `seq`, and a deleted id is never reused because it keeps `maxseg`. After a process crash the marker can be one flush behind the disk; after an OS crash, because the rename is not directory-synced, it can be older by the flushes since the last directory fsync, which happens at rotation, at `Close` and before any deletion (decisions 39, 40, 65). Either way a stale marker hides records and never exposes them, and `quill recover` or the writer's next open republishes it. |
| 9 | **One offset file per consumer**, `consumers/{name}`, written (temp, fsync, rename) only by the process holding that consumer's lock (`consumers/{name}.lock`, `flock`); used by in-process and external consumers alike. The file holds `<log id> <next> <protect>`, where `protect` is `0` or `1` (decision 57). Opening a handle or `register` creates it if absent, at the first retained sequence (decision 41). `Commit(next)` accepts any value from the first retained sequence to `Head + 1`, including a rewind (decision 36). **Accepted 2026-10-28.** | An external consumer cannot write a file the log's writer owns, and the writer's retention needs to see every consumer. One mechanism for both removes a code path. Each file has exactly one writer, so no cross-process merge is needed. Cost: each `Commit` is a file write and fsync, so a consumer commits once per batch, not per record (confirmed 2026-10-28). |
| 10 | **Sequences are contiguous.** The next sequence after open is the last valid frame's sequence plus one; if `quill.tail.seq` is greater than that, acknowledged data is missing and `Open` fails with `ErrCorrupt` (decision 39). `Head()` is the last *flushed* sequence. The numbers of a crashed unflushed suffix are reassigned. There is no separate durable-sequence call. | Readers and consumers see only durable records, so nobody can hold an unflushed number; the reference's gaps existed because several shards flushed independently. Callers must `Flush` before acknowledging a sequence upstream, which the reference's docs already require. A deviation from the reference. **Accepted 2026-10-28.** |
| 11 | **`OpenReader(dir)` is lock-free** and returns a `*Reader` with `Read`, `ReadWait`, `Scan`, `ScanAll`, `Records`, `Follow`, `OffsetForTime`, `Head`, `Stat`, `Check`, `Consumer` and `Close`. It re-reads `quill.tail` and re-lists segments on each call, so there is no `Refresh`. `ReadWait` polls. A reader holds segment descriptors, so retention deleting a segment cannot break a read in progress. | The stated need: another process consumes lazily. A damaged or missing segment is a hole: reads stop before it with a `GapError` (decision 38), and there is no option to skip one silently. |
| 12 | **Nothing holds back retention by default.** No consumer is protected unless it asks (decision 57). The in-memory `Dropped` counter counts segments deleted while some consumer had not read past them, per log, and resets on restart. **Accepted 2026-10-28.** Verified on the reference: its log-wide switch is a plain `bool` (off) and its server never sets it. | Consequence for a lazy consumer: unless it is protected it finds nothing if it starts after `Retention`, so `Retention` must exceed the worst delay of an unprotected consumer, be negative, or the consumer must be protected. A persisted counter is not built. |
| 13 | **Each log has its own flush goroutine.** Within a log, a flush holds the log's lock through write and fsync, as the reference does. Moving the fsync outside the lock is a measured follow-up. | Logs then flush in parallel by construction. The reference flushes its topics serially, so T dirty topics cost T fsyncs back to back (**verified** in its source; the cost is not measured). |
| 14 | **No dependencies.** `go.mod` has no `require` line. | Smallest possible audit and build surface. A check that needs a dependency is copied with the reason written in the file. |
| 15 | **Segments are read with `pread`: no mmap, no segment cache, no vendored code.** The log keeps the active segment's descriptor open and a read is one `ReadAt` into a pooled buffer, bounded by the durable position and decoded in place (`Scan` payloads alias the buffer and are valid only during the callback). Every other read opens the segment, reads and closes it. A small descriptor cache, or a mapped read path for sealed segments, is a measured follow-up (roadmap). | **Measured** on the reference's access pattern (a 8 MiB segment, 141-byte frames, CRC checked, 100 records per read, warm cache, single thread; macOS host and Linux container): a cached mapping took 2.1–2.7 µs per read and a held-open `pread` 4.3–4.6 µs; open-per-call took 5.8 µs (Linux) and 14.8 µs (macOS); a map-and-unmap per call took 7.3–8.3 µs (Linux) and 20.5 µs (macOS). Draining a 512 MiB backlog decoded 42–43 M records/s mapped against 34–35 M with `pread` on Linux, 37.6 against 33–34 on the host. Both are far above any durable write rate, so the extra 2 µs per read does not matter where a consumer's work is real. What `pread` removes: the cache and its reference counting, the vendored code and its third-party notice, the remapping needed to see appended bytes (the reference maps the active segment afresh on every read for that reason, **reported**), and the class of crash where a truncated mapped file faults a reader (**reported**: the reference fixed one such crash and lists the rest as a limitation). With cross-process readers (decision 11) and a writer that truncates a torn tail on recovery, that class matters here. Not measured: a backlog larger than memory read from a real disk, where sequential `pread` with large chunks should be limited by the disk either way (**inferred**); phase 4 measures it. Supersedes the earlier plan to wrap `syscall.Mmap`. **Accepted 2026-10-28**, with the real-disk backlog measurement as a phase-4 check. |
| 16 | **Limits are the reference's where they still apply:** payload at most 64 MiB − 32 bytes (so the frame body stays within the limit recovery enforces, decision 69), a declared frame over 64 MiB is corruption, segment file at most 1.5 GiB, `SegmentBytes` at most 1 GiB. Consumer names `[a-z0-9_-]`, 1–200 characters, a leading underscore reserved (decision 41). A log's name is its directory's name and quill imposes no limit on it. | They protect the file system and bound allocation. The 230-byte topic limit existed because a topic became part of a segment file name; it goes with decision 4. |
| 17 | **`quill.lock` lives inside the log directory** and the writer's `flock` is taken on it. There is no call that removes a directory under the lock. | The reference kept the lock beside the directory so a truncate-the-directory option could delete it while holding the lock. Without that option the directory is self-contained. A caller who wants an empty log removes the directory first. |
| 18 | **`At` is whole Unix seconds**, so retention is meaningful at second granularity only. | It is part of the frame. |
| 19 | **Linux and darwin only.** Other platforms do not build. | The directory lock is a unix `flock`. |
| 20 | **The source is split by responsibility**, none over about 600 lines. | The reference's core is one file of about 3,300 lines, which cannot be audited in one sitting. |
| 21 | **The performance gate is a recorded baseline** for each benchmark in phase 4 (six runs, one machine), with no later regression beyond run-to-run noise. | Quill changes shape, not speed, and a number invented in advance would be arbitrary. The orientation figures in [scope.md](scope.md) come from the reference at one lane. Quill's flush adds a marker write and fsync to the data fsync (decision 8), so durable-write throughput is expected to be lower; the baselines state that cost and do not hide it. |
| 22 | **No `LICENSE` while the repository is private**; no third-party code ships (decision 15), so no `THIRD-PARTY-NOTICES`. | Unlicensed means all rights reserved until release; the owner decides when a licence lands. **Confirmed 2026-10-28.** |
| 23 | **v0-forever versioning**, with the format marker versioned independently of the module. | Tags `v0.y.z`, never `v1`; a stable format is expressed as a frozen marker, not a major version. |
| 24 | **`MaxBytes` is per log and is checked at every segment seal as well as every prune pass.** The active segment is never deleted. It overrides consumer protection (decision 57). Default off, **accepted 2026-10-28**. | A time window alone does not bound size. Checking at the seal bounds the overshoot to one segment and one batch (decision 46); the reference checks only on a timer, so a burst can overshoot by a whole interval (**reported**). The default stays off so data is not deleted by a number the owner never chose; `check` warns on an unbounded log. |
| 25 | **`MinFreeBytes`** (default off): measured with `syscall.Statfs` on the log's directory, checked at each seal and prune pass. Below the floor the log deletes its own oldest sealed segments; with none left to delete, appends fail with an error wrapping `ENOSPC`. Like `MaxBytes` it overrides consumer protection (decision 57). | The backstop when several logs or other programs share a disk and no global budget exists. The reference lists it as not planned (**reported**); with one log per directory it is the only way to react to the disk's actual state. `Statfs` is standard library on both platforms (**verified** on macOS, compiled for Linux). It cannot free another process's bytes and `Bavail` excludes reserved blocks. |
| 26 | **`MaxPayloadBytes`**, default and ceiling 64 MiB. A record-count cap is separate (decision 33). | Cheap and lets a log refuse a runaway record at the door. |
| 27 | **`Roll()`** seals the active segment on demand; the `roll` CLI verb works offline only, because it needs the writer's lock. | A segment must be sealed before it can be archived or reached by retention. A live writer calls it in-process. There is no control socket to reach a running writer from the CLI. |
| 28 | **Archiving is a consumer.** `quill archive` is a **protected** consumer named `_archive` that copies sealed segments to a destination directory with CRC verification and writes the destination's `quill.tail` and `quill.format`, so an archive is itself a log that `OpenReader` can open. It runs beside a live writer (it reads only immutable sealed segments). | Reuses decision 9's machinery instead of adding a hook. Disk caps still win, so archiving can fall behind under pressure; that is the right priority for a rolling log. Shipping archives elsewhere is the operator's `rsync`. |
| 29 | **`quill.policy`** (strict JSON): the `Config` the writer last opened with — every retention and cap setting, `ConsumerTTL`, segment size and payload limit. Informational: `Config` at open is authoritative and rewrites the file. Offline tools read it. It is parsed tolerantly (unknown fields ignored) and a parse failure never blocks `Open`; an offline tool that cannot parse it refuses to act on it (decision 48). | A log is managed as a directory, and a tool looking at one directory cannot know its limits otherwise. **Accepted 2026-10-28.** |
| 30 | **Disk-full and write-failure behaviour** (decision 37): a flush writes at the durable offset and, on any write error, truncates back to it and keeps the records buffered (up to `MaxBufferBytes`, then appends fail fast with an error wrapping the cause); an **fsync** error is fatal and sticky. Quill adds tests that run both for real. | The reference derived its disk-full behaviour from its code but never ran it on a real full disk (**reported**). A container with a small `tmpfs` covers space exhaustion; short writes and fsync failure need the fault-injecting file-system seam (decision 52). |
| 31 | **`ConsumerTTL`** (default off). A protected consumer is **stale** as defined in decision 45; it then stops protecting segments (the TTL applies to protected consumers only). Its file is never deleted automatically; `Stat().StaleConsumers` reports it. A caught-up consumer is never stale. | The reference has no expiry (**reported**; its guide says a registered consumer that never commits pins segments forever), so one dead consumer can hold the disk until a cap fires. The mtime is free: every `Commit` and `register` writes a new file (inferred; tested). Keeping the file means a returning consumer resumes instead of restarting at 0 and reprocessing everything; deleting is an explicit `DeleteConsumer`. The default stays off because silent expiry changes who keeps their data. **Accepted 2026-10-28** (default off). |
| 32 | **Disk use is measured, not estimated.** `Stat().Bytes` is the sum of segment sizes; `Stat().Records` is `Head − first retained + 1` minus the records inside holes (hole sizes follow from contiguity). The size estimate `records × (average payload + ~16)` is for planning only. | **Verified** on the reference at one lane: its byte count equalled the bytes of the segment files at four payload sizes, and framing was 13.9–17.9 bytes per record. Contiguous sequences (decision 10) make the count exact where the reference's would not be. |
| 33 | **`MaxRecords`** (default off): keep roughly the newest N records, evaluated in the same pass and at the same seals as `MaxBytes`, segment-granular, never deleting the active segment. It does not replace `MaxBytes`. | Requested by the owner and **accepted 2026-10-28**: with the count and the record size known, a count is a natural way to say how much to keep. A count bounds disk only if record size is bounded, so the worst case is `MaxRecords × (MaxPayloadBytes + 32)`; `MaxBytes` remains the hard guarantee. Cheap: per-segment counts come from the first and last sequence. |
| 34 | **Write durability is a setting over one mechanism.** `Flush` makes records durable; `Sync(ctx, seq)` waits for a sequence to be durable, as group commit (producers append under the lock, release it, and wait for the next flush covering their sequence); `Config.SyncAppends` makes every append do that. The default is buffered. Consumer protection is documented as a retention setting only. | The format and the guarantees do not depend on the mode, so this is a policy, not a design commitment. The wait reuses the flush broadcast that `ReadWait` already needs. A flush holds the log's lock through its write and fsync (decision 13), so appenders queue behind it; waiters hold no lock, and the next flush covers everything appended meanwhile, so concurrent producers still share one fsync. `Sync` signals the flusher at once, so a lone producer does not wait for `FlushInterval` (decision 42). A failed flush returns the error to the caller, but the records stay buffered and may still become durable, so an error from `Sync` means *unknown*, not *lost*, and a producer that retries must tolerate duplicates (decision 37). A four-producer measurement on one log scaled about 3.5× over one in a container (**measured**, noisy; not measured on the host), which suggests flushes already overlap at the filesystem, so the gain over a plain `Flush` loop is unproven. **Accepted 2026-10-28.** |
| 35 | **Readable output: `-json` on `quill cat`, `read` and `tail`.** Newline-delimited JSON, one object per record: `seq`, `at`, `time` (RFC 3339 UTC), `len`, and exactly one of `payload` (a JSON string, only when the bytes are valid UTF-8) or `payload_b64`; `-b64` forces base64. The verbs read through `OpenReader`. **Requested by the owner 2026-10-28; the field layout accepted with the rest of this log.** | The segment files are binary (see scope.md), so a human or a script needs a way to see records. A lossless encoding matters more than a pretty one: Go's JSON encoder silently replaces invalid UTF-8, so a payload that is not valid UTF-8 must take the base64 path, and a test pins it. Newline-delimited objects stream, pipe into `jq`, and cannot be corrupted by a payload that contains a newline because JSON escapes it. |
| 36 | **A consumer's committed offset is the next sequence to read.** `Commit(next)`; the idiom is `Commit(lastRead+1)`; the next read starts at the offset; `Lag = Head + 1 − offset`; a consumer is *behind* when `offset ≤ Head`; a caught-up consumer has `offset = Head + 1`. `Commit` accepts values from the first retained sequence to `Head + 1` and refuses others (`ErrOffsetRange`). A consumer file stores the log ID; a consumer whose stored ID differs from the log's fails with `ErrWrongLog`. An offset above `Head + 1` found at open (a log restored to an older state) fails the handle with `ErrAhead`. **Accepted 2026-10-28.** | The Concepts table already defines an offset as the sequence a reader starts from. "Last processed" would make the stored value and the read start differ by one and invite off-by-one bugs; "next to read" makes them the same number. Without the ahead and wrong-log checks, a restored or recreated log silently skips new records until the head catches up to a stale offset. |
| 37 | **A failed flush never appends after a partial write, and an fsync error is fatal.** A flush writes with `pwrite` at the durable offset (`quill.tail.off`); on any write error it truncates the file back to that offset and keeps the records buffered, and the next attempt starts at the same offset. An fsync error puts the log in a failed state: every later `Append`, `Flush` and `Sync` returns an error wrapping `ErrFailed` until the log is closed and reopened, and recovery re-reads what is really on disk. **Accepted 2026-10-28.** | Retrying an append after a short write leaves [durable][partial frame][whole buffer], whose repeated sequences end the scan and hide acknowledged records. On Linux a failed fsync can clear the dirty-page error, so a retry can report success for data that never reached the disk (known behaviour, **reported**; not tested here). Space exhaustion is a write error and recovers by itself; an fsync failure does not. Refined by decision 60. |
| 38 | **Reads never skip a gap.** `Read` and `Scan` return a `*GapError{From, To}` when the records at the requested position are unavailable: deleted by retention (an offset below the first retained sequence) or missing or unreadable in the middle (a hole). At load, each segment's first sequence is compared with the previous segment's last, so a hole is found even when the damaged file cannot be parsed, and so is a segment deleted by hand. The consumer advances only by an explicit `Commit(To+1)`. `Stat()` reports `First` and the holes. **Accepted 2026-10-28.** | Silent skipping defeats "committing past the highest sequence read is safe", and a consumer cannot tell loss from being caught up. Contiguity (decision 10) makes holes detectable by arithmetic. Retention deletes only the oldest segments, so a middle hole is always damage or operator error. |
| 39 | **Recovery treats the marker as a lower bound and parses forward.** Let the marker name segment S at offset X. A segment is *sealed* exactly when a higher-numbered segment exists (nothing is written to mark it). Every byte of a sealed segment, and every byte of the newest segment below X (or below 0 when the marker names an older segment), was durable, so damage there is **corruption**: the file is never modified, a hole is raised for readers (decision 38), and if it is the newest segment `Open` fails with `ErrCorrupt`. In the newest segment, from X (or from byte 0 when the marker names an older segment), recovery parses forward and accepts each frame that is intact (CRC), within the length limit, and whose sequence is exactly one more than the previous accepted frame's; it truncates at the first frame that is not, and trusts nothing after it, whatever it contains, so an intact-looking frame embedded in a payload is never reached. The marker is therefore only a hint to where to start, and a stale marker loses nothing. If the log holds frames and its last valid sequence is below `quill.tail.seq`, acknowledged data is missing and `Open` fails with `ErrCorrupt`; if it holds no frames, the next sequence is `quill.tail.seq + 1`. **Known residual:** damage to bytes between a stale marker and the true end of the newest segment looks like a torn tail and is truncated, so acknowledged records there can be lost silently; the marker is made durable (directory fsync) at every rotation, at `Close` and before any deletion (decision 65), which bounds that window to the flushes within one segment. **Accepted 2026-10-28** (the owner chose parse-forward over a directory fsync on every flush). | A pure offset rule (truncate everything at or above the marker) contradicts decisions 8 and 40: after an OS crash the marker can lag the fsynced data by many flushes, and acknowledged records would be truncated, so the crash property test would fail against its own design. Parsing from a known frame boundary with sequence continuity keeps what the offset rule was for (no forged frames, no power-loss hole mistaken for damage) without making the marker durable on every flush, which would add a third fsync (about 20 ms on macOS). |
| 40 | **Durability of commits and of the marker is stated exactly.** Creating a log is decision 62. A `Commit` is temp, fsync, rename with no directory fsync: it survives a process crash, and after an OS crash it may roll back to an earlier value but never forward, so consumers are at-least-once. The `quill.tail` rename has no directory fsync either, so after an OS crash the marker may be older by the flushes since the last directory fsync, which happens at rotation, at `Close` and before any deletion (decisions 39, 65); a stale marker hides records from readers and loses none. | The earlier text claimed a commit was "durable when it returns" and a marker at most one flush stale; neither holds after an OS crash. A stale offset or marker is harmless (redelivery, hidden records). **Accepted 2026-10-28.** |
| 41 | **Consumer lifecycle.** Opening a handle or `register` creates the offset file if absent, at the first retained sequence, so a protected consumer (decision 57) is protected from the moment it exists. Temp files are named `.tmp-<random>`, ignored by every scan and removed when the writer opens the log. A consumer file that cannot be parsed protects every segment from the first retained one (the safe side) and makes `check` report UNHEALTHY. `DeleteConsumer` and `unregister` take the consumer's lock, delete only the offset file, and leave the lock file in place for good. Consumer names are `[a-z0-9_-]`, 1–200 characters; a leading underscore is reserved (`_archive` is the archiver). A process that only reads needs read access; one that holds a consumer needs write access to `consumers/`. | Without a file there is no protection, so a lazy consumer was exposed until its first commit; unlinking a lock file lets two processes hold the same consumer; and on a case-insensitive filesystem `A` and `a` would share one offset file but not one lock. **Accepted 2026-10-28.** |
| 42 | **`Sync` mechanics.** `Sync(ctx, seq)` signals the flusher immediately; a `seq` above the last assigned sequence returns `ErrBadSeq`; waiters still pending at `Close` get `ErrClosed` unless their sequence became durable; an error from `Sync` means unknown, not lost (decisions 34, 37). | A lone synchronous producer would otherwise wait up to `FlushInterval`, and a `Sync` on an unassigned sequence would block until its context expired. **Accepted 2026-10-28.** |
| 43 | **Sealing and the active segment.** A segment is *sealed* exactly when a higher-numbered segment exists; nothing is written to mark it. The newest segment is the active one and may be empty: its base sequence is then the last frame's plus one, or `quill.tail.seq + 1` when the log has no frames. `Roll` and age rotation first flush, and do nothing when the active segment has no frames. Rotation order: write and fsync the data, create the new empty segment, fsync the directory, publish the marker naming the new segment at offset 0. A crash before the create leaves the old segment newest; a crash after the create and before the marker leaves a marker naming a sealed segment, which recovery handles because a sealed segment is verified whole (decision 39). A sealed segment with no frames is corruption. Each crash point is tested. | Ranges and holes come from first frames, so an empty sealed segment would break the arithmetic and never age out; a rotation that crashed between create and publish left a marker naming a non-newest segment that no rule classified. **Accepted 2026-10-28.** |
| 44 | **Retention has a guard against a wrong clock.** `At` comes from the writer's wall clock. A prune pass deletes at most 25% of a log's sealed segments by age (at least one) and logs a warning through the configured logger when it would have deleted more; `quill prune -force` lifts the limit. `check` flags records whose `At` is more than a day in the future or earlier than the record before. | A clock stepped forward (an NTP correction, a VM resume, a device that boots at 1970 and then syncs) makes every sealed segment look expired, and one pass would delete them all. A rate limit gives an operator time to notice; it does not remove the hazard. **Accepted 2026-10-28** (25% per pass). |
| 45 | **`ConsumerTTL` measures how long unread data has waited, with no in-memory state.** A protected consumer is stale when it is behind (`offset ≤ Head`) and both its offset file's mtime and the `At` of the record at its offset are older than the TTL; the prune pass reads that one frame. A caught-up consumer is never stale, and one that is behind but commits regularly is not either. | Using mtime alone marks a caught-up, idle consumer stale the moment new records arrive after a quiet period longer than the TTL, and a "first saw it behind" timestamp kept in memory resets whenever the writer restarts, so a writer restarted more often than the TTL would never age anyone out. mtime is also reset by `cp` and `rsync`, so tests set it explicitly. Refines decision 31. **Accepted 2026-10-28.** |
| 46 | **Size limits are consistent.** `MaxBatchBytes` (default 16 MiB) is the largest encoded batch; a larger one is refused. An empty buffer accepts any single record up to `MaxPayloadBytes`, whatever `MaxBufferBytes` says. `Open` refuses a `MaxBytes` below twice `SegmentBytes` (`ErrConfig`). The disk bound is `MaxBytes + SegmentBytes + MaxBatchBytes`. A cap may delete up to one segment past its target. | The earlier bound was unbounded for large batches, a 64 MiB record exceeded the 1 MiB buffer cap, and a `MaxBytes` below one segment could never hold. **Accepted 2026-10-28.** |
| 47 | **Segment ranges come from first frames.** Because sequences are contiguous, a sealed segment's range is `[first, next segment's first − 1]`, so a `Log` or `Reader` reads only the first frame of each segment (a few bytes, cached per immutable segment id), binary-searches the list, and never scans a segment to learn its maximum. The active segment's range ends at `quill.tail.seq`. A reader exposes the marker's age. | A `Reader` has no in-memory index; this gives it the segment ranges for one small read per segment, and decision 63 gives it the rest. The marker's age is the only liveness hint a reader gets. **Accepted 2026-10-28.** |
| 48 | **State-file tolerance and versioning.** `quill.policy` is informational and parsed tolerantly. Any change to the shape of `quill.tail`, `quill.format` or a consumer file bumps the format marker; an older binary refuses a newer marker. | A strictly parsed informational file would make older tools refuse a log for an added field, while the files that matter must stay strict. **Accepted 2026-10-28.** |
| 49 | **Delivery semantics are stated.** Consumers are at-least-once: commit after processing; commit before processing for at-most-once; exactly-once needs processing that is idempotent on `seq`. | 87 | **`quill.ReadPolicy(dir)`** is exported: it returns `quill.policy` as a `Config` with only the policy fields set, or `ok == false`, so `quill prune` and `quill ls` act on the writer's settings and refuse a policy they cannot parse (decision 68). **Phase 4, 2026-10-28.** | The command lives in another package and cannot read the unexported decoder; a public, tolerant reader is the smallest surface that serves it. |
| 88 | **The release build and the scaffold's build script.** `build/quill` refuses a dirty or untagged tree (`--dev` builds the working tree as `dev-<sha>`), cross-compiles `cmd/quill` for linux and darwin on amd64 and arm64 with `-trimpath` and the version stamped in, writes one archive per target, `SHA256SUMS`, and a CycloneDX 1.5 SBOM naming the module and the Go toolchain (the only components). The house skeleton's `--cli|--server [user@host]` deploy form is not built: quill has no server and nothing to install on a host. **Phase 4, 2026-10-28.** | Decision 70 asks for version stamping, an SBOM, a refusal of a dirty or untagged tree and release archives; the deploy half of the skeleton's script serves daemons, which quill is not. |
| 89 | **The marker is fsynced into the directory at every rotation**, as decision 65 states; the phase-2 build fsynced the directory after creating the segment but not after the marker rename, which the phase-4 self-review found. **Phase 4, 2026-10-28.** | Without it the marker could be older than a rotation after a power loss, which recovery tolerates but which widens the stale-marker window decision 39 bounds to one segment. |
| 90 | **Benchmarks and the figures in the design documents.** T24's drain benchmark takes its backlog size from `QUILL_BENCH_BACKLOG_BYTES` (256 MiB by default) and the baselines record a run that fits in memory; the larger-than-memory measurement of decision 15 was then run on the owner's Linux server with a 12 GiB backlog against 8 GiB of memory (`docs/audits/benchmark-baselines.md`): about 330 MB/s, slower than the disk and than the warm decoder because the two run in series; a read-ahead is the measured follow-up. Figures in scope.md and review.md that came from the private reference are either replaced by quill's own baselines or softened to "the reference measured" without numbers. **Phase 4, 2026-10-28.** | Decision 70 asks for the replacement before the repository goes public; a figure the public cannot reproduce is softened rather than repeated. |
| 91 | **The read window starts at 64 KiB and doubles with each further read, up to 1 MiB.** A `Read` of a hundred records costs one small `pread`; a scan that keeps going soon reads a megabyte at a time; verification, recovery and `Check` start at 1 MiB. **Phase 4, 2026-10-28.** | The first Linux baselines showed a 100-record read near the tail costing about 73 µs against about 22 µs on the macOS build machine: the window read a fixed 1 MiB for every call, and copying a megabyte out of the page cache dominated. Measured, not guessed: the baselines before and after are in `docs/audits/benchmark-baselines.md`. |
| 92 | **A real crash-without-sync run is part of the release evidence.** `hack/powertest` and `docs/audits/power-loss.md`: a writer acknowledging flushed batches in an fsynced file, the machine rebooted with `sysrq b`, and the recovered log verified against the acknowledgements. It is run by hand on a machine that can be crashed, not in the gate. **Phase 4, 2026-10-28.** | The simulator's model (decision 61) was an assumption about real filesystems until a real machine was crashed; the owner provided one. The run found the marker stale and the data intact, which is what the model predicts and what parse-forward recovery (decision 39) handles. |
| 93 | **A prune pass deletes only the segments it chose.** The pass publishes the marker before unlinking (decision 65); when a rotation had failed earlier (decision 60 d) that publish seals the oversized active segment and runs the caps (decision 24), which delete a prefix of the sealed list through a nested pass. The outer pass records the segments it chose before publishing and afterwards deletes only those still at the front; a segment the nested pass sealed or spared is never taken on the outer choice. **Phase 4, 2026-10-29.** | The A1 audit (correctness-21) found the outer pass indexing its old count into the shortened list: a panic, or the deletion of unexpired records and of a protected consumer's unread segment beyond what the cap required, breaking decisions 24 and 57. Skipping the caps at that one seal would keep the count valid but deviate from decision 24's "checked at every segment seal"; re-deriving the choice keeps it literal. |
| 94 | **A `Reader` caches a sealed segment as bad only when the file is damaged, not when it could not be opened.** A segment that is not a regular file, is over the size limit, or has an undecodable first frame is cached as bad (a hole, decision 83). An error from the lstat or open itself (too many open files, permission denied, a file briefly missing) makes the segment a hole for that one view and is not cached, so the next view looks again. **Phase 4, 2026-10-29.** | The A1 audit (correctness-26) found one transient `EMFILE` turning a healthy sealed segment into a permanent hole for the life of the `Reader`, with every read of its range a `GapError` until the process restarted. Damage is a fact about the file and sealed files are immutable, so caching it is right (decision 83); an I/O error is a fact about the moment. |
| 95 | **`Close` leaves the active descriptor open while a read holds it.** `Close` marks the active segment retired and closes its file at once only when no read is in flight; otherwise the last in-flight read's release closes it, the rule rotation already follows (decision 43). The directory lock and the final flush are unchanged (decision 53): the lock is released at `Close` whether or not a read still holds the descriptor. A read already in flight when `Close` runs completes with its records; a read that begins afterwards returns `ErrClosed`. **Phase 4, 2026-10-29.** | The A1 audit (correctness-22) found `Close` setting the descriptor to nil while a `Read`, `Follow`, `Seek` or `Archive` that had taken its view still read through it outside the lock: a nil dereference in the reading goroutine, on a type documented as safe for concurrent use. Retiring the segment as rotation does needs no new mechanism; the descriptor is read-only, so outliving the lock harms nothing. |
